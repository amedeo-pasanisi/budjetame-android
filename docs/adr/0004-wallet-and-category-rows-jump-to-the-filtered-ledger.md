# Wallet and Category rows jump to the filtered ledger, with Edit demoted to a trailing button

A Wallet row's or a Category row's whole-surface tap no longer opens the entity's edit modal — it now sends a **ledger jump** (web issues #90/#93/#94, ported for web v1.2.0 parity): the shell glides to the Transactions page and the ledger arrives pre-filtered to exactly that Wallet or Category, its previous wallet/category/date/recurring filters replaced, its search cleared (input and debounced needle together), and its Filters panel closed, with the chips line showing the applied filter and a Frozen Wallet landing on the read-only banner. Editing moved to a trailing ✎ button on the same card — a sibling of the tap surface, never nested inside it — and Frozen Wallet rows gained the web's trailing Unfreeze button next to it, so no tap target on the row edits or unfreezes anymore.

Android's whole-row-tap-to-edit was a native convenience, but the parity goal (the two apps must read and behave alike) won: the tap surface now answers the question the row itself poses — "what happened with this Wallet/Category" — and the row's content (name, type, balance) is its affordance. The alternatives — keeping whole-row edit on Android (the apps would teach opposite row gestures), a long-press menu (discoverable only by accident, and the web has no such gesture), or an overflow ⋯ (extra tap to reach a one-tap action the web keeps visible) — each buys a native pattern at the cost of the shared interaction vocabulary the product is built on.

The jump is shell state, not screen state, and the plumbing follows from the pager (ADR-0003): the request can fire from the Wallets or Categories page while the Transactions page is disposed, or indeed before it has ever been composed (its ViewModel is created lazily on first visit). The shell therefore holds one pending request; the Wallets/Categories screens fire it through a callback; the Transactions screen consumes it exactly once — seeding the ViewModel's very first fetch when the page is new (so the ledger never flashes unfiltered and never fetches twice, the web's initial-state seeding) or applying it to the alive ViewModel when the page exists (riding the existing filter-change reload, like the web's while-mounted effect). A newer request replaces an unconsumed one, and an open Import Draft changes nothing: the jump applies underneath it (the ledger keeps refetching in the background per ADR-0002), so the user exits the draft to find the ledger already filtered.

Chosen over the alternatives — the request reaching the ViewModel directly from the row (a page-scoped ViewModel may not exist yet, and the shell owns the tab switch anyway), or each screen re-deriving the filter from navigation arguments (the pager has no navigation graph, ADR-0003) — because one pending slot at the shell mirrors the web's keep-alive model exactly and keeps the consume-once guarantee in one place.
