# The Transactions tab pins its chrome; only the records scroll

On the web app the Transactions toolbar (search + Filters toggle), the filtered chips line, the frozen-wallet banner, and the open filter panel all scroll away with the page. On Android they stay: the toolbar row is fixed chrome under the tab header, and the chips line, banner, and open panel are sticky list-head items above the records — the list is the only thing that scrolls, exactly like the Categories tab's pinned search bar, which already set the Android pattern. Only in the extreme case — the open panel's pinned stack taller than a short screen's content area — do the sticky items scroll away with the records instead of clipping.

The web's scroll-everything layout is cheap on a desktop wheel; a phone list is a different surface: with the tab's chrome pinned above a long paged ledger, the search and the Filters toggle stay one thumb-reach away while scanning (the filter state is the whole point of the screen — ADR-0002 keeps the list revalidating under any chrome), and the chips line keeps the active filters readable mid-scroll. This is a deliberate divergence from the parity target, bounded to chrome placement: the visual vocabulary (type scale, corners, shadows, spacing) still mirrors the web, and the ledger rows themselves behave and read the same. The Categories precedent is the honest native adaptation of the same web screen — its search bar was pinned for the same reason, and Transactions now joins it.

The cost is list room: the pinned stack — toolbar, and, when present, chips, banner, and panel — reduces the viewport the records get, most when the panel is open on a small phone. The alternative — keeping the web's fully scrolling chrome for literal parity — was rejected because it makes the screen's primary controls (search and filter) reachable only by scrolling back to the top, which the Categories tab already taught users they never have to do.
