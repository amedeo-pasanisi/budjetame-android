# The five tabs live in one finger-following horizontal pager, not a navigation back stack

The shell's five tabs (Dashboard, Wallets, Transactions, Categories, Recurring) now sit in a single HorizontalPager — one page per tab, the dashboard the start page — replacing the NavHost over the five tab routes, because the wanted interaction is a pager's native one: the content follows the finger while dragging with the neighbor page live underneath, a release snaps to the nearest tab, and a fling crosses exactly one tab, whereas Navigation Compose only animates between whole destinations and cannot follow a finger at all (the web app's release-to-switch swipe was rejected for the same reason — here the pages track the drag). The chrome around the pager is unchanged: the AppHeader and the bottom NavigationBar stay fixed and only the content area pages, the bar's selection follows `pagerState.currentPage` so drags light it up live, and a bottom-tab tap calls `animateScrollToPage` with a ~250 ms tween so taps and drags feel like one motion. Nested scrolling falls out of the platform: a horizontally scrollable card inside a page (the dashboard's trend chart) keeps a drag until its own edge, then the pager takes over through the standard nested-scroll chain, and dialogs own their windows and are unaffected.

This replaces the mechanism ADR-0002's keep-alive ran on: a tab's ViewModel no longer lives on a nav back-stack entry that survives while another tab is shown — with the pager there are no entries, and `viewModel {}` inside the pages resolves to the Activity's ViewModelStore. The keep-alive behavior survives the mechanism change: a page far offscreen is disposed once the pager settles, but its ViewModel stays in the Activity store, so returning to a tab renders instantly from held data and its background revalidation (the ADR-0002 data-version bump) keeps running, and the per-tab transient UI state the back-stack entries' saved-state registry used to keep — ledger and dashboard scroll positions, the Recurring tab's Costs/Incomes side, anything `rememberSaveable` holds — is retained the same way by a SaveableStateHolder keyed per tab around each page. The Import Draft still survives tab switches because it lives in the Transactions tab's ViewModel, which the Activity store keeps.

Two new rules follow, both accepted costs of dropping the back stack. First, sign-out and account deletion must clear the Activity's ViewModelStore in BudjetameApp's callbacks before the auth state flips: nothing in the pager ever disposes a tab ViewModel (BudjetameApp swaps to the LoginScreen without recreating the Activity), so without the explicit clear a second account would see the previous session's screens and data; clearing is now the app's own job instead of the navigation graph's, and it also drops the login screen's stale form state with the tab state. Second, the back button changes meaning: with no in-app back stack there is nothing to step back through, so a back press exits the app from any tab (an accepted change over today's stepping back through visited tabs), with open dialogs still closing first on their own windows. Chosen over the alternatives — keeping the NavHost and overlaying drag gestures (two competing navigation models, janky mid-drag), or scoping each page to its own ViewModelStore and clearing manually per tab (more machinery for the same result) — because the pager is the platform's one honest model of finger-following pages.
